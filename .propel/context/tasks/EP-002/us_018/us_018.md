# User Story - US_018

## Story ID

- ID Format: US_018

## Story Title

- Appointment Search and Slot Booking

## Description

- As a **patient**, I want to search for available appointment slots by provider or specialty and book a slot with double-booking prevention via optimistic concurrency locking, so that I can secure an appointment time without risk of conflicts.

## Acceptance Criteria

### AC-01: Slot search returns available appointments by provider

- **Given**: The patient is on the appointment search page (SCR-005)
- **When**: The patient searches by provider name
- **Then**: The system displays available time slots for that provider sorted by date/time, showing provider name, specialty, date, start time, and end time

### AC-02: Slot search returns available appointments by specialty

- **Given**: The patient is on the appointment search page (SCR-005)
- **When**: The patient searches by specialty (e.g., "Cardiology")
- **Then**: The system displays available time slots across all providers in that specialty sorted by date/time

### AC-03: Slot selection acquires a 30-second Redis lock

- **Given**: The patient has search results displayed
- **When**: The patient selects a time slot
- **Then**: The system acquires a Redis distributed lock on the slot with a 30-second TTL, displays a countdown timer (UXR-502), and navigates to the booking confirmation page (SCR-006)

### AC-04: Booking confirmation creates appointment record

- **Given**: The patient has a locked slot and is on the booking confirmation page (SCR-006)
- **When**: The patient confirms the booking
- **Then**: The system creates an Appointment record with "Scheduled" status, marks the AvailabilitySlot as unavailable, releases the Redis lock, generates a confirmation PDF, and sends it via email

### AC-05: Concurrent booking attempt on locked slot is rejected

- **Given**: Patient A has locked a slot and is reviewing the booking confirmation
- **When**: Patient B attempts to select the same slot
- **Then**: Patient B receives a "This slot is temporarily held by another user. Please select a different time." message and the slot appears as unavailable in their search results

### AC-06: Lock timeout releases slot automatically

- **Given**: A patient has locked a slot but does not confirm within 30 seconds
- **When**: The 30-second TTL expires
- **Then**: The Redis lock is released, the slot becomes available to other patients, and the patient sees a "Slot hold expired — please select again" message

### AC-07: No available slots shows guidance message

- **Given**: The patient searches for slots
- **When**: No slots match the search criteria
- **Then**: The system displays "No available slots found" with suggestions to try alternative dates or providers

## Edge Cases

- **Slot booked between search and selection**: If a slot displayed in search results is booked by another user before this patient selects it, the system should show an updated "Slot no longer available" message and refresh results
- **PDF generation failure**: If the confirmation PDF cannot be generated, the appointment is still created and a text-only email confirmation is sent with a note that the PDF will be sent separately
- **Email delivery failure**: If the confirmation email fails, it is queued for retry (max 3 attempts with exponential backoff) and the booking still succeeds
