# User Story - US_037

## Story ID

- ID Format: US_037

## Story Title

- AI Model Versioning and Accuracy Monitoring

## Description

- As an **admin**, I want the system to track which AI model version was used for each extraction operation and monitor accuracy metrics over time, alerting when the AI-Human Agreement Rate drops below 98%, so that model quality is continuously measured and regressions are caught early.

## Acceptance Criteria

### AC-01: Model version is recorded per extraction operation

- **Given**: The ML.NET NER pipeline processes a document
- **When**: ExtractedDataRecord entries are created
- **Then**: Each record includes the ModelVersion identifier used for that extraction (e.g., "NER-v1.2.0")

### AC-02: AI-Human Agreement Rate is calculated per model version

- **Given**: Staff have verified extracted data (accepted, modified, or rejected fields)
- **When**: The accuracy monitoring job runs
- **Then**: The system calculates the Agreement Rate as (accepted + accepted-with-minor-edit) / total-verified-fields for each model version, stored as a time-series metric

### AC-03: Alert triggers when Agreement Rate drops below 98%

- **Given**: The Agreement Rate for the current model version is being monitored
- **When**: The rate drops below 98% over a rolling 30-day window
- **Then**: The system sends an alert to admin users via the notification system and logs a critical event

### AC-04: Model version history is viewable by admin

- **Given**: Multiple model versions have been used over time
- **When**: An admin reviews the model performance
- **Then**: The system provides a report showing each model version, date range of use, number of documents processed, and Agreement Rate

### AC-05: Code mapping accuracy is tracked separately

- **Given**: Staff have verified ICD-10/CPT code mappings
- **When**: The accuracy monitoring job runs
- **Then**: Code mapping Agreement Rate is calculated separately from entity extraction Agreement Rate, with independent threshold monitoring

## Edge Cases

- **Insufficient verification data**: If fewer than 50 fields have been verified in the rolling window, the Agreement Rate should be reported as "Insufficient data" rather than triggering a false alert
- **Model version upgrade mid-batch**: If the model version is updated while documents are queued for processing, the system should record the actual version used (not the configured version) for each document
- **Agreement Rate recovers**: If the rate drops below 98% and then recovers above 98%, the alert should be auto-resolved with a recovery notification
