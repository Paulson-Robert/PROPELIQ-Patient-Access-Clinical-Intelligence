# User Story - US_030

## Story ID

- ID Format: US_030

## Story Title

- Manual Form Intake

## Description

- As a **patient**, I want to complete my pre-appointment intake using a traditional structured form with real-time inline validation, so that I can enter my medical information in a familiar form-based interface.

## Acceptance Criteria

### AC-01: Structured form displays all intake fields

- **Given**: The patient navigates to the manual intake page (SCR-010)
- **When**: The page loads
- **Then**: The form displays structured fields for medical history, current symptoms, medications, allergies, and reason for visit with appropriate input types (text, textarea, date pickers, multi-select)

### AC-02: Real-time inline validation on field entry

- **Given**: The patient is filling out the intake form
- **When**: The patient enters data in a field and moves to the next field (on blur) or types (on change for required fields)
- **Then**: The system validates the field inline and displays validation feedback immediately — green checkmark for valid, red border with error message for invalid (UXR-504)

### AC-03: Required fields prevent submission when empty

- **Given**: The intake form has required fields (e.g., reason for visit)
- **When**: The patient attempts to submit the form with required fields empty
- **Then**: The system highlights all empty required fields with validation errors and scrolls to the first error, preventing form submission

### AC-04: Successful submission stores intake record

- **Given**: All required fields are filled with valid data
- **When**: The patient clicks "Submit Intake"
- **Then**: An IntakeRecord is created with IntakeMode "Manual", linked to the appointment and patient profile, and the patient sees a "Intake completed successfully" confirmation

### AC-05: Submit button shows loading state during submission

- **Given**: The patient clicks "Submit Intake"
- **When**: The form submission is processing
- **Then**: The submit button displays a loading spinner (UXR-501) and is disabled to prevent duplicate submissions

### AC-06: Form data persists on network failure

- **Given**: The patient has entered data in the form
- **When**: The form submission fails due to a network or server error
- **Then**: The system preserves all entered data in the form, displays a retry option, and does not clear the form fields

## Edge Cases

- **Large medication list**: If a patient enters more than 20 medications, the form should display a scrollable list with add/remove controls without layout breaking
- **Special characters in medical history**: The form should accept and correctly store special characters (accented letters, medical symbols, abbreviations)
- **Browser back button during intake**: If the patient navigates away via browser back button, the form data should be preserved if they return via forward navigation
