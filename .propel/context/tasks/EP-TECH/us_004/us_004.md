# User Story - US_004

## Story ID

- ID Format: US_004

## Story Title

- Background Job Infrastructure with Hangfire

## Description

- As a **developer**, I want Hangfire Community integrated with PostgreSQL storage for background job processing, so that asynchronous workflows (document processing, notifications, calendar sync, slot swap monitoring) have a reliable, dashboardable execution engine.

## Acceptance Criteria

### AC-01: Hangfire server starts and processes a sample job

- **Given**: The backend API is running with Hangfire configured and PostgreSQL storage connected
- **When**: A fire-and-forget job is enqueued via `BackgroundJob.Enqueue(() => Console.WriteLine("test"))`
- **Then**: The job appears in the Hangfire storage, is picked up by the Hangfire server within 15 seconds, executes successfully, and its status transitions from Enqueued → Processing → Succeeded

### AC-02: Hangfire dashboard is accessible with authentication

- **Given**: The backend API is running
- **When**: An authenticated admin user navigates to `/hangfire`
- **Then**: The Hangfire dashboard renders showing job queues, succeeded/failed counts, and server information; unauthenticated requests to `/hangfire` return HTTP 401

### AC-03: PostgreSQL storage tables are created

- **Given**: The backend API has started at least once with Hangfire configured
- **When**: The developer queries PostgreSQL for Hangfire tables (`SELECT table_name FROM information_schema.tables WHERE table_schema = 'hangfire'`)
- **Then**: The query returns Hangfire's required tables (job, state, server, counter, hash, list, set) confirming PostgreSQL storage is operational

### AC-04: Recurring job scheduling is functional

- **Given**: Hangfire is running with PostgreSQL storage
- **When**: A recurring job is registered via `RecurringJob.AddOrUpdate("health-check", () => ..., Cron.Minutely)`
- **Then**: The job executes on the configured schedule and appears in the Hangfire dashboard's Recurring Jobs section with its next execution time displayed

## Edge Cases

- **Dashboard auth bypass**: If Hangfire dashboard authorization filter is misconfigured, the middleware should default to denying all access (fail-closed) rather than allowing unauthenticated access to job data
- **Job table creation failure**: If Hangfire cannot create its PostgreSQL schema (insufficient permissions), the application should log the error and fail at startup rather than running without background job capability
- **Stale server cleanup**: If a Hangfire server crashes without graceful shutdown, the next server instance should detect and clean up stale server records within the configured heartbeat interval
