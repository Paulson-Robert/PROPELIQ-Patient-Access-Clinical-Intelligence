# User Story - US_005

## Story ID

- ID Format: US_005

## Story Title

- Monitoring and Observability Stack Setup

## Description

- As a **developer**, I want Serilog structured logging, Sentry error tracking, and Uptime Robot availability monitoring configured, so that the platform can detect, diagnose, and alert on production issues to maintain ≥99.9% availability.

## Acceptance Criteria

### AC-01: Serilog captures structured log entries

- **Given**: The backend API is running with Serilog configured
- **When**: An API request is processed (e.g., `GET /health`)
- **Then**: Serilog writes a structured log entry to the console sink and file sink (if configured) containing timestamp, log level, message template, and request metadata (path, method, status code, duration) in JSON format

### AC-02: Sentry captures unhandled exceptions

- **Given**: The backend API is running with a valid Sentry DSN configured in environment variables
- **When**: An unhandled exception occurs (e.g., a test endpoint throws `InvalidOperationException`)
- **Then**: The exception is captured by Sentry with full stack trace, request context (URL, method, headers), and environment metadata, and appears in the Sentry dashboard within 30 seconds

### AC-03: Health check endpoint returns system status

- **Given**: The backend API is running with health checks configured
- **When**: A monitoring service sends `GET /health`
- **Then**: The endpoint returns HTTP 200 with a JSON body containing individual check results for database connectivity, Hangfire availability, and Redis connectivity (when configured), with each check reporting `Healthy`, `Degraded`, or `Unhealthy`

### AC-04: Uptime Robot monitors the health endpoint

- **Given**: The application is deployed to a publicly accessible URL
- **When**: Uptime Robot is configured with a 5-minute HTTP monitor targeting `GET /health`
- **Then**: Uptime Robot reports the endpoint status, sends alerts on consecutive failures (≥2 checks), and tracks uptime percentage visible in the Uptime Robot dashboard

### AC-05: Log levels are configurable per environment

- **Given**: The Serilog configuration uses `appsettings.{Environment}.json` overrides
- **When**: The application runs in Development environment
- **Then**: The minimum log level is `Debug`; when running in Production, the minimum log level is `Warning`, filtering out verbose request logs without code changes

## Edge Cases

- **Sentry DSN misconfiguration**: If the Sentry DSN is invalid or missing, the application should start normally with Sentry disabled and log a warning — not crash at startup
- **Health check timeout**: If a health check dependency (database, Redis) is slow to respond, the health check should timeout after 5 seconds and report `Degraded` rather than hanging indefinitely
- **Uptime Robot false positive**: If a transient network issue causes a single health check failure, Uptime Robot should require 2 consecutive failures before alerting to avoid false positives
