# User Story - US_047

## Story ID

- ID Format: US_047

## Story Title

- PHI Encryption at Rest and In Transit

## Description

- As a **developer**, I want all patient data (PHI) encrypted at rest using AES-256 via pgcrypto for database fields and ASP.NET Core Data Protection API for application-level encryption, with TLS 1.2+ enforced for all data in transit, so that the platform meets HIPAA encryption requirements.

## Acceptance Criteria

### AC-01: PHI columns are encrypted at rest with pgcrypto

- **Given**: The database schema includes PHI columns (PatientProfile: FirstName, LastName, DateOfBirth, Phone; IntakeRecord: MedicalHistory, CurrentSymptoms, Medications, Allergies)
- **When**: PHI data is written to the database
- **Then**: The values are encrypted using pgcrypto symmetric encryption (AES-256) and stored as encrypted bytea; raw column values are not human-readable via direct SQL query

### AC-02: PHI is decryptable only through application layer

- **Given**: PHI data is stored encrypted in the database
- **When**: The application reads PHI columns through EF Core
- **Then**: The Data Protection API decrypts the values transparently, and the application receives plaintext values for rendering — but direct database queries without the application's encryption key return encrypted data

### AC-03: TLS 1.2+ is enforced on all API endpoints

- **Given**: The ASP.NET Core backend is configured
- **When**: A client connects to any API endpoint
- **Then**: The connection uses TLS 1.2 or higher; connections using TLS 1.0 or 1.1 are rejected

### AC-04: Redis connections use encrypted transport

- **Given**: The application connects to Upstash Redis
- **When**: A Redis operation is performed
- **Then**: The connection uses TLS-encrypted transport (rediss://) — no plaintext Redis connections are permitted

### AC-05: Encryption key management uses secure storage

- **Given**: Encryption keys are required for pgcrypto and Data Protection API
- **When**: Keys are stored and accessed
- **Then**: Keys are stored in environment variables or a secure vault (not in source code, not in appsettings.json), with key rotation support built into the architecture

### AC-06: HTTPS redirect enforced for all requests

- **Given**: A client makes an HTTP (non-TLS) request to the API
- **When**: The request is received
- **Then**: The server returns a 301 redirect to the HTTPS equivalent URL and includes HSTS headers (Strict-Transport-Security)

## Edge Cases

- **Missing encryption key on startup**: If the encryption key environment variable is not set, the application should fail to start with a clear error message: "PHI encryption key not configured — application cannot start without ENCRYPTION_KEY"
- **Key rotation**: When encryption keys are rotated, existing encrypted data should remain readable with the old key while new data is encrypted with the new key (dual-key support during transition)
- **Performance impact of field-level encryption**: Encryption/decryption overhead should not add more than 50ms to API response times for typical queries
