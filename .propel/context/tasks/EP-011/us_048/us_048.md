# User Story - US_048

## Story ID

- ID Format: US_048

## Story Title

- API Rate Limiting

## Description

- As a **developer**, I want API rate limiting enforced on all public-facing endpoints using Redis sliding window counters, returning HTTP 429 with Retry-After headers when limits are exceeded, so that the platform is protected against brute-force attacks and abuse.

## Acceptance Criteria

### AC-01: Rate limits are enforced per endpoint

- **Given**: API endpoints are configured with specific rate limits (e.g., login: 10 requests/minute, general API: 100 requests/minute)
- **When**: A client exceeds the configured limit for an endpoint
- **Then**: The system returns HTTP 429 (Too Many Requests) with a Retry-After header indicating the number of seconds until the limit resets

### AC-02: Sliding window counter uses Redis

- **Given**: Rate limiting is active
- **When**: A request is processed
- **Then**: A Redis sliding window counter tracks the request count per client IP (or authenticated user) per endpoint, using atomic INCR operations with TTL-based window expiry

### AC-03: Rate limit response includes standard headers

- **Given**: A client makes an API request (within or exceeding limits)
- **When**: The response is returned
- **Then**: The response includes X-RateLimit-Limit (max requests), X-RateLimit-Remaining (remaining requests), and X-RateLimit-Reset (timestamp of window reset) headers

### AC-04: Login endpoint has stricter rate limits

- **Given**: The login/authentication endpoint is configured
- **When**: A client sends more than 10 login requests within 1 minute
- **Then**: Subsequent login requests return HTTP 429, protecting against credential brute-force attacks

### AC-05: Security headers are included on all responses

- **Given**: Any API endpoint is called
- **When**: The response is returned
- **Then**: The response includes security headers: X-Content-Type-Options: nosniff, X-Frame-Options: DENY, Content-Security-Policy, and Cache-Control: no-store for authenticated endpoints

### AC-06: Fallback to in-memory when Redis unavailable

- **Given**: Redis is unreachable (quota exhausted or service down)
- **When**: A rate-limited request is processed
- **Then**: The system falls back to in-memory sliding window counters per process instance, with a warning logged

## Edge Cases

- **Distributed deployment**: In a multi-instance deployment, Redis-based rate limiting ensures consistent limits across all instances; in-memory fallback is per-instance and may allow higher aggregate throughput
- **Authenticated vs. anonymous**: Authenticated users should be rate-limited by user ID; anonymous users should be rate-limited by IP address
- **Rate limit bypass for health checks**: Health check and monitoring endpoints should be exempt from rate limiting to avoid false downtime alerts
