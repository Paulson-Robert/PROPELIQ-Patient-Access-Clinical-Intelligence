# User Story - US_044

## Story ID

- ID Format: US_044

## Story Title

- Immutable Audit Logging

## Description

- As an **admin**, I want an immutable, append-only audit log that automatically records all PHI access events, staff actions, and system state changes with timestamp, actor ID, action type, and affected resource, so that HIPAA compliance is maintained through complete activity traceability.

## Acceptance Criteria

### AC-01: Audit entries are created automatically for all commands

- **Given**: The MediatR pipeline is configured with an audit logging behavior
- **When**: Any command handler (state-changing operation) executes
- **Then**: An AuditLog entry is automatically created with Timestamp, ActorUserId, ActorRole, ActionType, ResourceType, ResourceId, Details (JSONB), and IpAddress — without requiring manual audit calls in each handler

### AC-02: Audit log is append-only at database level

- **Given**: The AuditLog table exists in PostgreSQL
- **When**: Any SQL UPDATE or DELETE operation is attempted on the AuditLog table
- **Then**: The database rejects the operation via PostgreSQL rules or triggers, ensuring immutability

### AC-03: PHI access events are audit-logged

- **Given**: A staff member views a patient's 360-Degree Patient View or clinical documents
- **When**: The PHI data is accessed
- **Then**: A read-access AuditLog entry is created recording who accessed whose data, when, and from which IP address

### AC-04: Authentication events are audit-logged

- **Given**: A user attempts to log in (success or failure)
- **When**: The authentication result is determined
- **Then**: An AuditLog entry is created with ActionType "LoginSuccess" or "LoginFailed", the user identifier, and the IP address

### AC-05: Admin actions are audit-logged

- **Given**: An admin performs user management operations (create, update, deactivate, role change)
- **When**: The operation completes
- **Then**: An AuditLog entry is created with the admin actor, the affected user, the action type, and the details of the change (old value → new value for role changes)

### AC-06: Audit entries include structured details

- **Given**: An auditable event occurs
- **When**: The AuditLog entry is created
- **Then**: The Details JSONB column contains structured metadata relevant to the action type (e.g., for role change: `{"oldRole": "Staff", "newRole": "Admin"}`)

## Edge Cases

- **Audit logging failure**: If the audit log insert fails (e.g., database connection issue), the original operation should complete but a critical error should be logged to Sentry and the next audit attempt should include the missed event
- **System-initiated actions**: Actions performed by background jobs (Hangfire) should be audit-logged with ActorUserId set to "SYSTEM" and ActorRole set to "System"
- **Bulk operations**: If a batch operation affects multiple resources, each affected resource should have its own audit entry — not a single entry for the batch
