# User Story - US_012

## Story ID

- ID Format: US_012

## Story Title

- Patient Data Cascade Deletion and Seed Data

## Description

- As a **developer**, I want a complete cascade deletion mechanism that permanently removes all patient data across all stores on patient request, and seed data scripts that populate the database with representative test data, so that HIPAA right-to-delete compliance is enforceable and the development team has realistic data for feature development.

## Acceptance Criteria

### AC-01: Cascade deletion removes all patient data from PostgreSQL

- **Given**: A patient with uploaded documents, extracted records, conflicts, intake records, appointments, notifications, code mappings, and risk factors exists in the database
- **When**: A data deletion request is executed for that patient
- **Then**: All records across PatientProfile, ClinicalDocument, ExtractedDataRecord, DataConflict, PatientView, MedicalCodeMapping, IntakeRecord, Appointment, Notification, CalendarSync, NoShowRiskFactor, and associated PreferredSlotQueue entries are permanently removed with zero orphaned records remaining

### AC-02: Cascade deletion clears patient data from Redis cache

- **Given**: A patient has active session tokens, slot locks, or cached data in Redis
- **When**: A data deletion request is executed for that patient
- **Then**: All Redis keys associated with the patient's user ID and session are deleted

### AC-03: Deletion is irreversible and audit-logged

- **Given**: A data deletion request is executed
- **When**: The deletion completes
- **Then**: An AuditLog entry is created recording the deletion actor, timestamp, patient ID, and a summary of deleted resource types — and the deleted data cannot be recovered

### AC-04: Seed data script populates representative test data

- **Given**: A clean database with the schema applied
- **When**: The seed data script is executed
- **Then**: The database contains at minimum: 3 users (1 patient, 1 staff, 1 admin), 5 availability slots, 2 appointments, 1 clinical document with extracted records, and sample ICD-10/CPT reference data

### AC-05: Seed data is idempotent

- **Given**: The seed data script has already been executed once
- **When**: The seed data script is executed again
- **Then**: No duplicate records are created; existing seed records are preserved or upserted without errors

## Edge Cases

- **Deletion of patient with no data**: Deletion request for a patient with only a User record (no profile, no documents) should complete successfully without errors
- **Concurrent deletion and data insertion**: If a document upload is in progress for a patient being deleted, the deletion should wait for the upload transaction to complete or roll back before proceeding
- **Audit log references to deleted patient**: AuditLog entries referencing the deleted patient should retain the patient ID for compliance traceability but the patient's personal data should not be recoverable from audit entries
