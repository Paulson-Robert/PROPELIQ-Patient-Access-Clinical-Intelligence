# User Story - US_011

## Story ID

- ID Format: US_011

## Story Title

- Appointment Scheduling and Notification Data Model

## Description

- As a **developer**, I want the database schema for appointment scheduling (provider availability slots, recurring patterns, booking statuses, preferred slot swap queues), no-show risk factor persistence, and notification delivery logging, so that the booking, notification, and risk scoring features have a complete data layer.

## Acceptance Criteria

### AC-01: AvailabilitySlot supports recurring schedule patterns

- **Given**: The AvailabilitySlot entity is configured
- **When**: A provider's recurring weekly schedule is created (e.g., Monday 9am-5pm, Tuesday 9am-5pm)
- **Then**: Slots are generated from the recurrence pattern with individual slot records containing StartTime, EndTime, IsAvailable, and RecurrencePattern fields

### AC-02: Appointment status tracking covers all lifecycle states

- **Given**: An Appointment record exists
- **When**: The appointment progresses through its lifecycle
- **Then**: The Status column correctly stores and transitions between Scheduled, Arrived, Completed, Cancelled, and No-Show states with UpdatedAt timestamp recorded at each transition

### AC-03: PreferredSlotQueue maintains first-come-first-served ordering

- **Given**: Multiple patients have registered preferred slot preferences
- **When**: A preferred slot becomes available
- **Then**: Queue entries are ordered by RequestedAt timestamp (ascending) and the Status column transitions from Waiting to Swapped or Expired

### AC-04: NoShowRiskFactor persists all four scoring inputs

- **Given**: A patient has appointment history
- **When**: A NoShowRiskFactor record is created or updated for the patient
- **Then**: The record stores HistoricalNoShowCount, AverageLeadTimeDays, PreferredTimeOfDay, IsNewPatient, and LastCalculatedAt with correct data types

### AC-05: Notification delivery log tracks retry state

- **Given**: A notification is dispatched for an appointment
- **When**: The notification delivery is attempted
- **Then**: The Notification record stores Channel (SMS/Email), NotificationType, Status (Queued/Sent/Delivered/Failed), RetryCount, LastAttemptAt, and FailureReason, supporting the exponential backoff retry pattern

## Edge Cases

- **Slot boundary overlap**: Two AvailabilitySlot records for the same provider should not have overlapping time ranges; the database should enforce this via a unique constraint or application-level validation
- **Orphaned queue entries**: When an appointment is cancelled, associated PreferredSlotQueue entries should be updated to Expired status
- **Notification channel independence**: SMS and email delivery failures should be tracked independently — an SMS failure should not block email delivery
