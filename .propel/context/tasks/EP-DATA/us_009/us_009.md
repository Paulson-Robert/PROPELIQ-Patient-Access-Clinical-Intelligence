# User Story - US_009

## Story ID

- ID Format: US_009

## Story Title

- Redis Integration and Session Infrastructure

## Description

- As a **developer**, I want Upstash Redis integrated into the backend for session caching, appointment slot locking with TTL-based optimistic concurrency, and rate-limiting counters, so that the platform can enforce concurrent access controls and API throttling within the free-tier budget.

## Acceptance Criteria

### AC-01: Redis connection is established and health-checked

- **Given**: The backend application is configured with Upstash Redis connection credentials
- **When**: The application starts up
- **Then**: The Redis connection is established successfully and the health check endpoint reports Redis as healthy

### AC-02: Session tokens are cached in Redis with sliding expiry

- **Given**: A user authenticates and receives a JWT session token
- **When**: The session is created
- **Then**: The session metadata is stored in Redis with a 15-minute TTL that resets on each authenticated request (sliding expiry)

### AC-03: Slot lock acquires and releases with 30-second TTL

- **Given**: A patient selects an available appointment slot
- **When**: The system acquires a distributed lock on the slot
- **Then**: A Redis key is created with a 30-second TTL preventing other users from locking the same slot, and the lock is released on booking completion or timeout

### AC-04: Rate-limiting counters enforce per-endpoint limits

- **Given**: An API endpoint is configured with a rate limit (e.g., 100 requests per minute)
- **When**: A client exceeds the configured rate limit
- **Then**: The system returns HTTP 429 (Too Many Requests) with a Retry-After header, using Redis sliding window counters for tracking

### AC-05: Redis quota fallback to in-memory cache

- **Given**: The Upstash Redis free-tier daily command quota (10K) is exhausted
- **When**: A Redis operation is attempted
- **Then**: The system gracefully falls back to an in-memory cache implementation with a warning logged, without disrupting user-facing functionality

## Edge Cases

- **Redis connection failure on startup**: Application should start with degraded mode (in-memory fallback) and log a critical warning rather than crashing
- **Slot lock contention**: If two users attempt to lock the same slot within milliseconds, only the first SETNX succeeds; the second receives a "slot temporarily unavailable" response
- **TTL drift**: Redis TTL precision should be validated to ensure 30-second slot locks do not expire prematurely under network latency
